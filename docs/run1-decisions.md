## R1-D0 — Architecture of the "central system" (how to centralise without regression)
Every redesigned page today hand-rolls the same shell inline:
`<div className="paj {variant}" data-category="{theme}">` + font `<Helmet>` +
`<header className="site-header">`(Navigation+AuthNav) + `<div className="breadcrumb">`
+ `<main>` + `<footer className="site-footer">`. `src/styles/part-aj.css` (scoped
`.paj`, auto-generated by `build-paj-css.mjs`) is the proven styling engine and the
approved look.

**Decision:** the central system is a thin React layer that emits the *same* `.paj`
markup from one place, plus a canonical theme attribute:
- `src/styles/central/themes.css` (NEW, hand-owned — does **not** touch the
  generated `part-aj.css`): defines the five themes keyed on `[data-theme]`
  (`vedic, birthday, mystic, science, neutral`) as `.paj[data-theme=…]` overrides
  mirroring the existing `[data-category]` values, and adds **neutral**.
- `src/components/central/`: `PajShell` (themed wrapper + SiteHeader + Breadcrumb +
  main + SiteFooter), `SiteHeader`, `SiteFooter`, `Breadcrumb`, `PageHeader` (the
  header block: eyebrow·H1·lead·trust), and 7 layout components (Tool, Report, Hub,
  Collection, Article, Money, Utility) that are thin configs over `PajShell`.
- Shell sets **both** `data-theme` (canonical) and `data-category` (kept so the
  existing generated CSS still themes the page) during the coexistence period.

Why: identical DOM/classes → zero visual change for migrated pages; other
categories keep using their inline `.paj` untouched (coexistence is allowed until
run 5); genuine centralisation — header/footer/theme/breadcrumb now change in one
place.
